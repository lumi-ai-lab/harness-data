## 4. 诊断：harness agent 跑 qdm-metric-cli 报 PROVIDER_UNAVAILABLE / EOF，用户外部终端正常

- **现象**：同一台机器、同一条命令（saleAmt, 2026-08-08, SALES_STORE_DAY_AVG），用户在自己的终端跑返回 `code:OK, saleAmt=15976.87`；新开 `pi --session` 也能通；唯独 harness agent 内的 Bash 连续多次 `PROVIDER_UNAVAILABLE / Post request failed: EOF`（resourceGroup=doris）。
- **已排除**：命令错误、网关/数据缺失（用户已证 OK）、`authz.mode=off`（harness-config.yaml）、沙箱（关闭沙箱仍 EOF）。
- **真因**：agent 的 Bash 环境被注入了 `HTTPS_PROXY=http://127.0.0.1:1082`，1082 端口监听进程是 **MacPacket（企业 VPN/安全客户端 HTTP 代理）**，并非 WorkBuddy 网关（应用网关在 18488=Electron PID 15893=`WORKBUDDY_STARTUP_PID`）。该代理无法把请求转发到 DataQL 网关 → EOF。
- **验证链**：清掉 HTTPS_PROXY 后，失败点从 `model:offline-customer` 推进到 `model:dal-manage-full-link-store-dc-article-info`（store/article 内部模型），说明公网网关可达但 doris 内部模型仍需 VPN 隧道；改走 18488 应用网关也不代理 DataQL。结论：本会话的 VPN/网络链路到 doris 后台不通，而用户的终端/新 pi 会话链路是通的。
- **可复用结论**：harness agent 内执行 data CLI 前，先 `echo $HTTPS_PROXY`；若是 `127.0.0.1:1082`(MacPacket) 且查询报 EOF，则该代理阻断了 DataQL。临时绕过：`env HTTP_PROXY= HTTPS_PROXY= ...` 直连（内部模型可能仍失败）；根治需保证该会话 VPN 对 DataQL 路由可用，或从已通的环境跑。数值以用户外部终端的真实返回为准，agent 侧未取到值时不编造。
